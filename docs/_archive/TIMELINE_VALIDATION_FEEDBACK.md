# Timeline検証フィードバック分析

## フィードバックの要点

### 検証項目
- ① 行動を把握できるか ◎（時系列＋アプリ＋サービス）
- ② 目的とのズレが分かるか ○（目的＋色分け）
- ③ 結果が分かるか △（Timeline単体ではなくResultと組み合わせる）
- ④ 「なぜ」が考えられるか ○（ヒント＋実際の行動）
- ⑤ 振り返りの負担 △（Reflection側で検証）
- ⑥ 次の行動を考えられるか △（現状は明示的な支援は少ない）

### 特に確認したいのは ②と④

## 注意点

### 「赤＝脱線」をどう扱うか
- YouTube = 悪い行動とは限らない（チュートリアルの可能性）
- Google = 調査も、必ずしも目的に必要な調査とは限らない
- 色分けは「アプリそのものの善悪」ではなく、「目的に対する行動の分類の仮説」として扱う

### 3分未満のイベントをフィルタリングする点
- VS Code 2分 → Google 1分 → VS Code 2分 が VS Code 5分 に見えてしまう可能性
- 閾値は「正しい値」と決めるのではなく、「仮設定」として扱う

## 検証の5つの問いかけ

### ①「自分が何をしていたか」が分かる？
- 「あ、この時間はエラーについて調べてたな」と思い出せるか

### ②「どこで目的から外れたか」が分かる？
- 「ここまでは予定通りだったけど、この辺から違うことをしている」と分かるか

### ③ 色分けに違和感がない？
- 「これは赤になっているけど、自分にとっては目的達成に必要だった」というケースがないか

### ④ 3分未満を消して問題ない？
- 実際の記録と比較して、「この消えた情報があれば原因が分かったのに」ということがないか

### ⑤ Timelineを見たことで「なぜ」が思い出せる？
- 「YouTubeを7分使っていた」だけで終わるのか
- 「エラーの解決方法を探していて、関連動画を見始めたんだった」まで思い出せるのか

## 考察

### 現在のフェーズ
- 実装フェーズ → 実使用による検証フェーズに移行
- 機能追加ではなく、検証を優先すべき

### 優先度
- 詳細表示機能は急いで実装しなくていい
- 閾値のカスタマイズ、ズーム、詳細表示、アイドル表示の改善は、実使用で困ったものから順番に考える

### 結論
- 現在のTimelineを実際に見て、過去の行動と、できなかった理由を理解できたかを確認すべき
- 1セッション使って、①〜⑥と、特にTimelineを見て気づいたことを記録すべき

## 次のステップ

1. 実際に1セッション使用して検証
2. 検証項目①〜⑥を評価
3. Timelineを見て気づいたことを記録
4. 色分けと閾値の妥当性を確認
5. 改善が必要な点を特定
