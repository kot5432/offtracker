## Phase 7.5: コア体験検証

### 目的
現在の実装を実際に使い、OffTrackerが本当に「なぜできなかったかを理解する」体験になっているかを検証する。

### 検証方法

#### 実際に使用するシナリオ
ユーザー自身が以下のパターンで実際に作業する：

1. **ケース1: 普通に作業**
   - 意図通りに集中して作業する
   - 目的を達成する

2. **ケース2: 途中で脱線**
   - 作業開始
   - 途中でYouTubeを見る
   - 作業に戻る

3. **ケース3: 難しい問題に遭遇**
   - 作業開始
   - エラー発生
   - 調査に行く
   - 作業終了

4. **ケース4: 時間不足**
   - 作業開始
   - 時間が足りなく終了

5. **ケース5: 目的達成**
   - 明確な目的を設定
   - 達成する

6. **ケース6: 目的未達**
   - 明確な目的を設定
   - 達成できない

### 検証指標

① 行動を正しく記録できたか
- ウィンドウ切り替えが検知されているか
- タイムスタンプが正確か
- アプリ名が正確か

② 目的と行動を結びつけられたか
- セッションが目的と紐付いているか
- イベントがセッションに紐付いているか

③ 結果を記録できたか
- 達成度を選択できたか
- できたことを記録できたか

④ なぜできなかったかを振り返れたか
- 原因を選択できたか
- 自由入力で補足できたか

⑤ Timelineを見ることで振り返りに役立ったか
- 行動の流れが視覚化されているか
- どこで離脱したかが分かるか

⑥ 過去データから繰り返しが見えたか
- 複数セッションを比較できるか
- パターンが検出できるか

### 成功基準
- ✅ ①〜⑥のうち少なくとも4つが「はい」と答えられる
- ✅ Pattern画面を見て「自分がなぜできなかったのか理解できる」と思える
- ❌ アプリをいろいろ使ったことが分かるだけなら、プロダクトとして弱い

## Phase 8: SQLite + Session基盤

### 目的
履歴・検索・集計を扱いやすくするためにSQLiteへ移行し、Sessionを中心としたデータ基盤を構築する。

### データ構造の再確認

#### 現在の問題点
- SessionとEventの紐付けが不完全（session_idが設定されていない）
- JSONファイルで分散保存（session.json, events.json, results.json, reflections.json）
- 履歴表示が困難

#### 改善後の構造
```
Session (1)
├── Purpose
├── Events (1..n)
├── Result (0..1)
└── Reflection (0..1)

Session (1..n)
    ↓
Pattern Analysis
```

### 実装手順

#### Step 1: SQLite導入
- `sqlite3` npmパッケージの追加
- データベースファイルの作成

#### Step 2: スキーマ実装
- DATA_MODEL.mdのスキーマをSQLiteで実装
- テーブル作成：sessions, events, results, reflections

#### Step 3: データ移行スクリプト
- 既存JSONデータのパース
- SQLiteへの挿入
- データ整合性の検証

#### Step 4: API更新
- SQLite操作に更新
- session_idの正確な紐付け
- トランザクション管理

#### Step 5: テスト
- データ永続性の確認
- リレーションの確認
- パフォーマンス確認

### 重要: AIに丸投げしない
以下の手順で実装：
1. 現在のJSON構造とDATA_MODEL.mdを比較
2. SQLiteスキーマ案を作成
3. 移行方法を検討
4. 実装計画を提示
5. ユーザー確認
6. 実装

## Phase 9: 目的→行動→結果→振り返り統合

### 目的
1つのSessionとして目的・行動・結果・振り返りを完全に統合する。

### 実装内容

#### Sessionデータの完全化
- SessionにPurposeを含める
- Eventsにsession_idを正確に設定
- ResultをSessionに紐付け
- ReflectionをSessionに紐付け

#### UIの改善
- Timelineでセッションごとの表示
- 過去のセッション一覧表示
- セッション選択機能

#### データフローの修正
```
Session開始
  → Session保存（SQLite）
  → トラッキング開始
  → Event記録（session_id付き）
  → Session終了
  → Result保存（SQLite）
  → Reflection保存（SQLite）
```

## Phase 10: 履歴・パターン分析

### 目的
過去の複数セッションを比較し、パターンを検出する。

### 実装内容

#### 履歴表示
- 過去のセッション一覧
- 日付、目的、結果、振り返りの表示
- セッション詳細の表示

#### パターン検出（AIなし）
- ルールベースのパターン検出
  - 未達成セッションの頻度
  - 原因ごとの集計
  - アプリ遷移パターンの分析
- 事実の集計を表示

#### AIの使用方法
- **AIにさせること**
  - 行動ログの要約
  - 過去セッションの整理
  - 共通するパターンの文章化
  - 振り返りを促す質問の生成

- **AIにさせないこと**
  - 「あなたの原因は○○です」と断定
  - 「集中力が低い」と評価
  - 「YouTubeを使ったから失敗した」と判断
  - 心理状態の推測

## データモデルの修正

### 必要な変更点

#### Sessionの完全化
```typescript
interface Session {
  id: string;
  purpose: string;  // 既存
  target_time_minutes?: number;  // 既存
  start_time: string;  // 既存
  end_time?: string;  // 既存
  status: 'active' | 'completed';  // 既存
  actual_duration_minutes?: number;  // 追加
  created_at: string;  // 追加
}
```

#### Eventのsession_id紐付け
- 現在: session_idが設定されていない
- 改善: セッション開始時にsession_idを設定

#### 1セッションの完全なデータ構造
```json
{
  "session": {
    "id": "session-001",
    "purpose": "ログイン機能を実装する",
    "start_time": "18:00",
    "end_time": "19:30",
    "actual_duration_minutes": 90
  },
  "events": [
    { "session_id": "session-001", ... },
    { "session_id": "session-001", ... }
  ],
  "result": {
    "session_id": "session-001",
    "result_level": "partially_completed",
    ...
  },
  "reflection": {
    "session_id": "session-001",
    "deviation_reason": "...",
    ...
  }
}
```
