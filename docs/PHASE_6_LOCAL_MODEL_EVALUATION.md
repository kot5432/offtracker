# Phase 6: PC内ローカルモデル比較

更新: 2026-10-14

## 結論

今回の用途では、評価したQwen3 0.6B、1.7B、4Bのいずれも現時点の製品候補として採用しない。4BはJSONとして読み込めた一方で、候補を出すべきでないケースでも作り話を含む候補を生成し、候補数と根拠の品質ゲートを全ケースで満たさなかった。品質を担保する検証を先に固定し、合格できる方式が見つかるまでモデルをアプリへ接続しない。

## 実行条件

- 対象: Qwen3 0.6B、Qwen3 1.7B、Qwen3 4B（Ollama）
- 実行環境: Windows 11相当、AMD Ryzen 7 7735HS、RAM 13.3 GiB。GPU推論は利用できずCPUで実行
- 入力: `docs/mock-sessions/phase-6-hypotheses.json` の合成3シナリオのみ。実セッション情報は未使用
- 共通プロンプト: `docs/PHASE_6_PROVIDER_EVALUATION.md` の「共通プロンプト」
- 出力: JSON Schema制約、根拠参照は `activity:0` / `result` の文字列形式
- 設定: temperature 0、seed 42、num_ctx 4096、num_predict 512、think false
- 生出力・計測値: [`phase-6-local-evaluation-simple-refs.json`](mock-sessions/phase-6-local-evaluation-simple-refs.json)
- Qwen3 4B 生出力・計測値: [`phase-6-local-evaluation-4b.json`](mock-sessions/phase-6-local-evaluation-4b.json)
- 前段の試行: [`phase-6-local-evaluation.json`](mock-sessions/phase-6-local-evaluation.json)、[`phase-6-local-evaluation-schema.json`](mock-sessions/phase-6-local-evaluation-schema.json)。根拠参照のオブジェクト形式を段階的に単純化し、最終試行で文字列形式に統一した

## 結果

| モデル | 平均応答時間 | 平均出力token | 形式・内容の主な問題 | 判断 |
|---|---:|---:|---|---|
| Qwen3 0.6B | 約4.9秒 | 約75 | 3ケースすべてで不足理由を適切に返せず、指示文の反復や汎用テンプレート、目的そのものを候補として出力。構造チェックでもcoverageの問題を検出 | 不採用 |
| Qwen3 1.7B | 約18.2秒 | 約242 | `mixed-activities`と`uncertain-short-partial`で同一タイトルの候補を3件ずつ生成。`short-completed`では候補なしが適切なケースに、内容の近い推測候補を3件生成 | 不採用 |
| Qwen3 4B Q4_K_M | 約44.4秒 | 約301 | 3ケースすべてで`coverage_message`を文字列`"null"`として返す。混合ケースは候補過剰、完了済みケースは無根拠な詳細と無効な根拠参照、関係不明ケースは候補抑制に失敗 | 不採用 |

### ケース別所見

- `mixed-activities`: 0.6Bは指示文を説明文へ流用。1.7Bは同一候補を3件に水増しし、活動の配分など独立した観点に分けられなかった。
- `short-completed`: 0.6Bはひな型のような候補を返した。1.7Bは完了済みの短い活動から、根拠不足を理由に候補を控えるべきところ、宛先・送信時期など入力にない詳細を複数候補へ展開した。
- `uncertain-short-partial`: 0.6Bは指示文の反復。1.7Bは同じ「未完了の活動」候補を3件出し、原因を明らかにできないことを適切に扱えなかった。

### Qwen3 4Bの追加所見

- `mixed-activities`: 3候補を生成し、ケースの期待上限を超えた。3件あるにもかかわらず`coverage_message`を`"null"`として返した。
- `short-completed`: 完了済みの短い活動から、遅延・内容不適切・宛先誤りを推測した。宛先誤りなど入力にない事実を追加し、存在しないActivity参照も含んだ。
- `uncertain-short-partial`: 関係不明の活動から、研究不足やコミュニケーションの影響を推測して候補を3件生成した。
- 1ケースあたり約43〜45秒、約10〜11出力token/秒。モデル取得直後の空きメモリは約2.85 GiBで、後続ケース前は約0.5〜0.76 GiBだった。現PCでは1.7Bより大幅に遅く、メモリ余裕も小さい。

1.7Bは3ケースすべてJSONとして読み込めたが、構文が正しいことは内容の根拠性を保証しない。今回の品質ゲートでは、候補の重複、入力外の詳細の補完、根拠不足時に候補を抑制できないことを重大な失敗として扱う。

## 比較後に追加した入力ゲート

記録済みの最終出力へ新しい条件を静的に当てはめると、0.6Bのcoverage欠落は出力検証で拒否される。1.7Bの同一タイトルは重複検証、完了済み・関連活動だけの候補は未達なし条件、全Activityが関係不明の候補は入力充足条件で拒否される。これは保存出力と条件を照合したもので、Rustコードのビルドや実行確認ではない。

Rust側には、これらの判断を推論呼び出し前に行う`validate_hypothesis_input`と、候補応答に入力ゲートを再適用する`validate_hypothesis_response`を追加した。プロバイダー呼び出し元はまだないため、呼び出し順の統合とコンパイル確認は今後の作業。

## 方式選定への提案

1. 4Bでも重大な内容失敗が残り、実行時間とメモリ負荷も増えたため、単純なモデル大型化では解決しない。アプリ接続前に、候補数・根拠参照・入力外主張・`uncertain`の扱い・空候補条件・JSON契約を機械的に検証する品質ゲートを定義する。
2. ルールベースで確実に組み立てられる事実表示と、モデルが作る仮説を分離する。モデル応答の根拠文は表示せず、許可された参照からローカルで生成する既存方針を保つ。
3. 次の方式比較は、同じ疑似3シナリオと採点表で、別の方式または改善した制約付き生成方式を評価する。外部方式では認証情報の取り扱いと送信前の同意設計を先に確定し、実セッションを送らない。
4. 重大失敗が出た時点で、その方式をそのまま製品採用しない。プロンプト変更で比較する場合は、全方式へ同じ変更を適用し、旧試行と新試行を別記録にする。

## 制約

これは3つの合成シナリオによる初期比較であり、モデル全般の性能や実利用時の正確さを示すものではない。追加6ケースの採点や、他のローカルモデル・外部方式との比較は未実施。Qwen3 4Bの結果も、この小さなケース集合だけに対する観察である。
