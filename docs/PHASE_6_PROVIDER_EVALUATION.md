# Phase 6: AI方式の品質比較手順

更新: 2026-10-14

## 目的と範囲

Cloudflare Workers AI、OpenAI API、PC内ローカルモデルを、同じ疑似セッション・同じ指示・同じ出力形式で比較する。評価対象は仮説候補の根拠性と扱いやすさであり、モデルの賢さ全般ではない。

実セッション情報は使わず、PC内のQwen3 0.6B/1.7B/4Bを疑似データで評価済み。結果と採否は `docs/PHASE_6_LOCAL_MODEL_EVALUATION.md` に記録する。OpenAI APIとCloudflare Workers AIは認証情報が未設定のため未実施。認証情報の有無だけを確認し、値そのものは読み出し・記録しない。

2026-10-14、Ollamaの起動時にユーザーデータフォルダーへの書き込み権限が不足していることを確認し、`C:\Users\kkyog\.ollama` に現在のユーザーの変更権限を追加した。その後OllamaのローカルAPIが起動し、Qwen3 4Bを取得して同じ疑似3シナリオを評価した。4Bも重大な品質課題を満たせず、実行時間は1ケース約44秒だった。詳細は `docs/PHASE_6_LOCAL_MODEL_EVALUATION.md` を参照。

## 共通プロンプト

各候補に同一のシステム指示とユーザー入力を渡す。温度など共通設定が可能なら固定し、設定値とモデルの正確な識別子を記録する。

```text
あなたは振り返りを助ける候補提示者です。原因を断定せず、入力にある根拠だけで最大3件の異なる仮説を作ってください。

制約:
- 入力にない感情、意図、予定、出来事、原因を補わない。
- evidenceは自由記述にせず、Activityを `activity:0`、結果を `result` で参照する。入力に存在する参照だけを使う。
- purpose_relationがuncertainの活動を、目的外だった証拠として扱わない。
- 候補同士を言い換えで水増ししない。
- タイトル120字以内、説明600字以内、coverage_message240字以内、根拠参照は1候補8件以内にする。指定JSON外の項目を追加しない。
- 根拠が足りなければ候補を0〜2件にし、coverage_messageで不足理由を説明する。候補が3件ならcoverage_messageはnullにする。
- 目的の未達だけから、特定の原因を断定しない。
- 評価、叱責、生産性スコアを含めない。
- 指定JSON以外の文章、Markdown、コードフェンスを出力しない。

出力形式:
{
  "hypotheses": [
    {
      "title": "可能性としての短い見出し",
      "description": "断定を避けた説明と、分からない点",
      "evidence": ["activity:0"],
      "confidence": "low | medium | high"
    }
  ],
  "coverage_message": "3件未満の場合の不足理由。3件ならnull"
}

次のJSONだけを分析してください:
<INPUT_JSON>
```

`<INPUT_JSON>` には `docs/mock-sessions/phase-6-hypotheses.json` の各シナリオと `docs/mock-sessions/phase-6-provider-cases.json` の各ケースの `input` だけを入れる。`display_example` と `evaluation_expectations` はモデルに渡さず、採点時にだけ参照する。最初の3シナリオは画面例との整合性、追加6ケースは失敗しやすい条件の確認に使う。

## 採点基準

各軸を0〜2点で評価する。点数は内部の品質比較にだけ使い、製品利用者の評価や生産性スコアには表示しない。

| 軸 | 0点 | 1点 | 2点 |
|---|---|---|---|
| 根拠の正確さ | 存在しない参照を使う、または候補説明が参照事実と矛盾 | 参照先は存在するが候補への結び付きが弱い | 参照先が存在し、候補を直接支える |
| 候補の独立性 | 複数候補が実質同じ説明 | 一部に重なりがある | 各候補が別の説明を示す |
| 不確実さの扱い | 原因を断定、または不明を無関係と誤読 | 留保はあるが不足理由が曖昧 | 分からない点と推測の限界を明示 |
| 候補数の調整 | 根拠のない候補を追加 | 候補数は妥当だが不足理由が弱い | 根拠のある数だけ示し、3件未満なら理由を説明 |
| 表現 | 叱責・評価・スコア、または誤解を招く表現 | おおむね中立だが曖昧 | 中立で読みやすく、利用者が修正できる仮説として表現 |
| 出力形式 | JSON不正、必須項目欠落、または禁止値 | 修正が必要な軽微な形式差 | 契約どおりでそのまま検証可能 |

合計点だけで選ばない。存在しない参照、候補説明への入力外事実の追加、`uncertain`を根拠にした目的外判定、JSON解析不能は重大な失格条件として記録する。各出力を同じ人が採点し、可能なら採点時に方式名を伏せる。

## 3つの疑似シナリオで見る点

| シナリオ | 必須の確認 |
|---|---|
| `mixed-activities` | 0〜2件の根拠ある候補にとどめる。調査・文書作成の時間配分と連絡の記録を別の観点にできるか。連絡の内容・必要性・中断を事実として作らない。重複する3件目を足さない |
| `short-completed` | 完了した短い活動から、無理に原因候補を作らない。候補なしと理由を返せる |
| `uncertain-short-partial` | 未完了の原因を断定しない。`uncertain`を目的外とみなさず、根拠不足を返せる |

画面の `display_example` は品質の参考例であり、語句の完全一致は求めない。根拠参照はプレビュー側でもローカル入力から表示文に解決する。根拠の正確さ、候補の差、候補なしを選べることを優先する。

## 追加6ケースで見る点

追加ケースの期待条件は `docs/mock-sessions/phase-6-provider-cases.json` に記載した。主に長時間を問題視しないこと、目的外の可能性と原因を混同しないこと、結果・活動が欠けたときに作り話で埋めないこと、関係不明を目的外扱いしないことを確認する。9ケース全てを最初から比較する必要はなく、まず既存3例で方式の初期比較を行い、重大な失敗が見つかったら追加ケースで再確認する。

## 結果の記録様式

方式ごと、シナリオごとに以下を残す。APIキー、アカウント識別子、実セッション内容は記録しない。

| 項目 | 記録内容 |
|---|---|
| 実施日時 | UTC日時 |
| 方式・正確なモデルID | 例: Workers AIのモデルID。ローカルはモデル名・量子化 |
| 実行条件 | 温度など、設定できた項目。未設定は未設定と記す |
| シナリオID | 上記3種類 |
| 出力 | 疑似データに対する生出力。機密情報がないことを確認して保存 |
| 採点 | 6軸の点数、重大失格の有無、短い理由 |
| 運用値 | 応答時間、入出力token数、推定費用。取得できなければ未計測 |
| 修正作業 | JSON修正の要否、画面表示での読みにくさ |

## 判断ゲート

1. まず3シナリオで各方式を1回ずつ実行し、リクエスト条件と出力を記録する。同じ条件で追加実行する場合は別試行として保存する。
2. 重大失格が一つでもあれば、その原因を分類し、プロンプト調整後に全方式で同じ条件を再実行する。
3. 3件の疑似例だけで本番プロバイダーを決めない。候補を絞った後、活動の長短・完了/未完了・目的関係を組み合わせた合成ケースで再評価する。
4. 外部方式を選ぶ場合は、APIキーをデスクトップアプリに含めず、バックエンド、送信前の同意、送信項目の説明、利用上限を別途設計する。実セッションの送信はその設計とユーザー同意が整うまで行わない。

## 次の実作業

ローカル比較で重大な失敗が確認されたため、次はアプリへモデルを接続せず、品質ゲート（重複候補、根拠外の断定、候補過剰、必須項目欠落）を先に固定する。追加6ケースは、別方式または改善版を比較する段階で実施する。外部方式は認証情報とプライバシー・同意設計が揃うまで未実施とし、実セッションを送らない。
