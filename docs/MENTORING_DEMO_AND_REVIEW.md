# 発表デモと利用者レビュー計画

更新: 2026-10-18

レビュー画面: `desktop/ui/review/reflection-review.html`。娯楽例では時間を決めたケースの次回時間、課題例では次に試す案を一度の選択で選べる。選択肢に加え、任意の自由記述欄を置く。各例で注目してほしい事実を強調している。自由記述はこの試作では保存しない。**この画面は架空データのレビュー用プロトタイプで、実セッションのインサイト生成機能ではない。** 今回の記録の完了画面は `reflection.html`。`pattern.html` は今回の振り返りを完了した後に必ず表示する画面ではなく、過去の記録を確認するための画面とする。レビュー記録: `docs/REFLECTION_REVIEW_LOG.md`。

## 発表で伝えること

OffTrackerは、セッションごとに異なる本人の目的（勉強・課題・娯楽など）に対し、PC上の行動記録と本人が選んだ結果を並べて振り返る。アプリを一律に良し悪し判定せず、気づきにつながる材料を示す。

## 発表で最も見せる部分

発表の主役は、記録の収集や分類の仕組みではなく、最後の振り返り画面とする。見せる順序は「本人の目的と実感」→「行動のどの流れ・切替が注目点か」→「その判断の根拠」→「本人が自分で考えられること」。見た人が、振り返りから何に気づけるのかを画面だけでも捉えられることを目指す。

- 目的から外れた可能性がある例では、該当する時点と前後の行動を示す。原因や意図は決めつけない。
- 目的に沿って進められた例では、役立った可能性のある流れや時間配分を示し、本人が意味づける余地を残す。
- 記録だけでは判断できない例では、結論を作らず、情報不足であることを明確にする。
- 個々のアプリ記録の列挙や分析精度の説明は補助とし、振り返りの注目点を理解するために必要な分だけ見せる。
- 前段の画面が未完成または説明に時間がかかる場合は、架空データを使ってよい。架空例であることを表示し、実機機能と混同させない。

画面構成と見た目の全面変更は、機能の流れが確認できた後に利用者が決める。その際は振り返りを視覚的な中心にし、前段の入力・記録は根拠として従属させる。

## 発表デモの流れ（約2分）

### 1. 目的を決める（Home）

画面: `desktop/ui/home.html`。実機デモなら、発表者が行うセッションの目的を一文で入力する。例: 「数学の課題を3問進める」。時間目標がある場合だけ設定する。目的なしの作業を記録して評価するアプリではなく、本人が決めた目的を振り返るための記録だと説明する。

話すこと: 「PCを開く目的は毎回違います。まず今回の目的を本人が決めます。娯楽でも課題でも同じ流れで使えます。」

### 2. 記録中の動きを示す（Home / Timeline）

実機デモでは短いシナリオを事前に実施し、発表時はその完了済みセッションを開く。記録中の画面では目的・経過時間・現在の対象アプリが見える。Timelineではアプリ等の記録と、Activity・目的との関係の参考分類を見せる。

話すこと: 「バックグラウンドではアクティブアプリなどを記録します。ここに見えるのはPC上の観測です。画面を見ていた理由や、集中していたかまでは分かりません。分類は参考情報です。」

### 3. 本人が結果を選ぶ（Result）

画面: `desktop/ui/result.html`。製品画面は既存DBと互換する5段階を表示する。目的と目標時間に加えて、PC上で記録された行動の順序・分類・時間を参考として示すが、実際に何を見たか・何ができたかは本人の判断とする。結果未選択なら中間値を補って保存せず、選択した場合に限り結果と任意補足を保存する。`desktop/ui/review/result-review.html` は3択を検討した過去の架空レビュー案であり、現在の製品画面とは異なる比較素材としてのみ使う。架空例は選択の参考で、実際の本人の記録ではない。文字入力は任意補足欄だけ。

話すこと: 「PCの記録だけでは、課題が何問できたか、動画を楽しめたかは分かりません。本人が目的と記録を見比べて、自分の実感を選びます。必要なら記録だけでは分からない事情を補足できます。」

### 4. 今回の流れから気づきを探す（Reflection）

画面: `desktop/ui/reflection.html`。ここをデモの中心として時間をかけて見せる。目的と本人の結果を起点に、注目する行動の流れ・切替、その根拠、本人が考える手掛かりを示す。気づきはアプリが決めつける結論ではなく、本人が記録と実感を照らして考える材料として説明する。発表用ダミーを使う場合は画面上の架空データ表示を残す。

話すこと: 「たとえば、調査の後に課題へ戻ったか、決めた時間内で楽しめたかを見返せます。この表示から次に何を変えるべきかを決めつけず、本人が必要なら次に試すことを考えます。」

### 5. 価値を一言でまとめる

「目的・PCの行動記録・本人の結果を一緒に見返し、自分の過ごし方に気づくためのアプリです。アプリを良い悪いで評価したり、毎回改善を求めたりしません。」

### 発表時の表示区分

| 区分 | 表示・説明 |
|---|---|
| 実装済みの実機機能 | Homeの目的設定・セッション記録、Resultの5段階入力・行動記録参照、Timelineのイベント表示、Reflection画面。発表で使用した実機セッションの結果だと説明する |
| 架空データのレビュー案 | `desktop/ui/review/reflection-review.html` と `desktop/ui/review/result-review.html`。架空データであること、入力が保存されないことを示す |
| 未実装・未検証 | 仮説の自動提案、入力文言の確定、初見利用者による有用性検証。完成済みとして説明しない |

実機画面と架空データ画面を同じセッションの記録に見せない。発表に使う実機セッションのID・目的・使用画面は事前にメモし、各画面を開く順序をリハーサルする。

## データの表示ルール

- 前段の機能が未完成の場合、固定のダミーデータを使ってよい。
- ダミー画面には常時「発表用の架空データ」と表示する。
- ダミー、実機取得、未実装の完成イメージを混在させない。
- 実際の気持ちや原因をログから推測して事実扱いしない。
- 「目的に合っていたか」は本人の目的と本人の振り返りが主であり、自動分類は参考情報とする。
- 振り返りの主な注目点と、その注目点を支える記録を視覚・説明の上で区別する。利用者が「だから何に気づけるのか」を自分の言葉で説明できるかを確認する。

## 利用者レビューで確かめること

画面を初見の人に見せ、説明を聞く前に次を尋ねる。

1. このセッションで本人が何を目的にしたか分かるか。
2. 画面のどの部分が記録で、どの部分が本人の結果や気づきだと思ったか。
3. 最後の画面から、今回どのような行動の流れだったか分かるか。
4. 画面を見てどんな気づき・疑問が生まれたか。
5. 目的が娯楽の場合にも、この振り返りが自然に感じられるか。
6. 入力で迷った箇所や、不要だと感じた項目は何か。

記録するもの: 説明なしで理解できた項目、誤解、入力にかかった時間、不要と感じた質問、予想外の反応、改善案。少人数の定性レビューとして扱い、一般化しすぎない。

## 機能レビューの現時点の判断

現行機能は「目的に対して何をしていたかを振り返る」ための土台であり、目的達成を証明するものではない。自動記録はアクティブアプリ等の観測であって、注意・意図・心理状態ではない。Activityや目的との関係分類は参考情報で、本人による修正が必要かどうかを利用者レビューで先に確かめる。AI仮説、長期パターン、専用の訂正UIは、振り返りから気づきが得られない理由が確認されるまで優先しない。

レビュー後は、結果に応じて必要な機能だけを選ぶ。

| 観察された問題 | 次に検討する機能 |
|---|---|
| 行動の誤分類が気づきを妨げた | Activityの簡単な補足・訂正 |
| 行動は分かるが背景が不足した | 影響の大きい短い任意質問を追加 |
| 選択肢の意味に迷った | 結果・理由の選択肢を簡素化または再定義 |
| 目的や入力元が分からなかった | 目的・自動記録・本人入力・参考分類の表示を改善 |
| 一回の記録では気づきが得られなかった | 目的を区別した任意の過去記録比較を検討 |
| 現行の事実表示だけで気づきが得られた | AIや追加入力を増やさず、現行体験を優先 |

## 達成度3択の比較案（製品UIには未採用）

| 選択肢 | 保存値 | 意味 |
|---|---|---|
| 目的に沿って過ごせた | `completed` | 目的に合う時間として本人が振り返る |
| 一部そうだった | `partially_completed` | 目的に沿った部分と別の部分があった |
| 今回は別のことをしていた | `not_completed` | 今回は設定した目的とは異なる過ごし方だった |

これは入力負担を確かめるために作った比較案。机上評価では部分達成の量や時間目標との両立が表現しにくいと分かったため、製品UIには採用せず5段階を維持した。3択の画面 `desktop/ui/review/result-review.html` は文言レビュー用の架空プロトタイプとして残す。保存値・過去データは変更しない。

### 結果段階と現行分析の関係（2026-10-19 更新）

| 保存値 | 画面上の表現 |
|---|---|
| `completed` | 目的に沿って過ごせた |
| `partially_completed` | 一部は目的に沿って過ごせた |
| `not_completed` | 今回は目的に沿って過ごせなかった |

画面では、本人が選びやすいよう達成度を3段階に整理した。現行の分析ロジックは `completed` とそれ以外を区別するだけで、5段階の細かな差を分析には使っていない。画面上の3択を選んでも、保存済みの既存5段階値を別値に書き換えない。既存値を表示するときは近い3択に対応させ、変更がない場合は元の保存値を維持する。選択は任意。未選択の場合は結果を保存せず、便宜的な中間値を作らない。PC上で記録された行動の順序・分類・時間は参考として表示し、目的の達成や本人の実感は自動判定しない。

### 画面遷移と「戻る」操作の明確化（2026-10-19）

今回の流れを「目的を決める → 結果を選ぶ → 行動記録を確認 → 振り返る → 完了」と各画面に表示する。TimelineのHome操作は振り返りを省略する選択であることをボタンと補足文で示す。ReflectionからTimelineへ戻る操作、完了画面からReflectionを見直す操作も、戻り先の内容を具体的に示す。曖昧な「前に戻る」「Homeに戻る」は使わない。

### 入力負担のレビューと改訂案（2026-10-18）

現行の製品UIを確認したところ、結果入力は3択だが、「一部そうだった」は達成度を指すのか目的との一致を指すのか曖昧で、作成者から既に意味の確認があった。DBは5段階を保存し、過去値の `mostly_completed`（ほぼ完了）と `minimal`（少し進行）は3択にまとめるため、細かな差が失われる可能性がある。加えて、結果画面の補足欄二つはどちらも任意の自由記述で用途が重なり、片方は「次回も続きを見る」といった次回メモにも使われている。

このため、直ちにDBや製品UIの選択肢を変えず、以下の文言案で意味と負担をレビューする。選択肢は「今回の目的に沿って過ごせた」「目的に沿った時間も、別の過ごし方もあった」「今回は別の目的で過ごした」。選択前に「今回の目的に対する自分の実感を選びます」と短く説明する。補足は一欄に統合し「補足したいこと（任意）」とする。説明は「記録だけでは分からない事情や、次に見返したいことがあれば書けます」とし、例として「解き方を調べていたので、Web閲覧も課題の一部だった」「次回は調べたページを先にメモしておく」を示す。毎回書かなくてよいことも伝える。結果の選択は任意のままとし、未選択時に中間値を自動保存する現行動作は、本人の実感を代弁するので見直し候補として記録する。

この3択案は既存5段階の全ての差を表せない。特に「ほぼ達成」と「少し進行」を別々に知る必要が分析・表示にあるかを、合成ケースで比較してから保存値の対応を決める。既存DB値・過去データはレビュー前に変更しない。次回確認では、娯楽（目標時間内に楽しめた／超過した）と課題（3問中2問できた／手を付けなかった）の例を示し、選択肢の意味を自分の言葉で説明できるか、選択に迷うか、補足欄が必要かを確かめる。

### 3択と既存5段階の情報差（合成ケース机上評価・2026-10-18）

目的: 3択案へまとめた場合に、保存済み5段階のどの違いが見えなくなるかを、架空の課題・娯楽ケースで確認する。これは利用者の理解度や分析性能の検証ではなく、選択肢設計の情報差を洗い出す机上評価。

| 架空の目的・本人の結果 | 3択案で近い選択 | 3択で保てる情報 | 失われる／迷う情報 |
|---|---|---|---|
| 動画を1時間楽しむ。45分楽しめた | 目的に沿って過ごせた | 目的と時間目標に沿った実感 | 予定より短かったことを区別しない |
| 動画を1時間楽しむ。1時間45分楽しめた | 目的に沿って過ごせた、または目的に沿った時間も別の過ごし方もあった | 楽しめたこと／時間を超えたことは補足欄で表現可能 | 目的の達成と目標時間超過の両立を一つの選択で表せない |
| 課題3問のうち2問を解いた | 目的に沿った時間も、別の過ごし方もあった | 目標の一部を進めた実感 | 「ほぼ完了」と「少し進行」を区別しにくい |
| 課題に着手して1問だけ進めた | 目的に沿った時間も、別の過ごし方もあった | 目的に沿った部分があったこと | 2問進行ケースと同じ選択になり、進行量の差が消える |
| 課題に着手せず、別の目的で過ごした | 今回は別の目的で過ごした | 今回の目的と違う過ごし方だった実感 | 未着手なのか、別目的を達成したのかの違いは補足が必要 |
| 目的は達成したが、本人が選択を飛ばした | 未選択で進む | 本人が回答を保留したこと | 現行製品処理は未選択を `partially_completed` にしてしまい、本人の実感と区別できない |

**机上評価の判断**: 3択は入力負担を下げるが、部分達成の程度や目標達成と時間超過の併存を失う。短い自由記述は文脈を補えるが、全員が書く前提にできない。したがって保存値を今すぐ3段階へ統合せず、製品の5段階を維持したまま、画面上の説明と任意の短い選択肢を初見レビューで比較するのが妥当。結果の選択は任意とし、未選択は未回答として保持する必要がある。DBの既存値・スキーマは変更しない。

**未解決**: 初見の人が5段階を過剰と感じるか、3択の方が選びやすいか、分析に部分達成の程度がどれほど必要かは未確認。これらは画面レビューと合成データで別途確認する。

## AI分析で必要な情報を調べる

まず合成セッションで、同じ分析を次の段階に分けて比較する。

- 最小: 本人の目的、Activityの種類・順序・時間、目的との関係、3択の結果
- 追加A: 本人が任意で選んだ短い振り返り項目
- 追加B: 本人が任意で書いた自由記述（外部送信しない評価を先に行う）

評価観点は、役立つ具体的な気づき、記録に沿った根拠、入力外の断定、娯楽目的の扱い、ユーザー操作数。情報を増やしたときの改善が小さければ追加質問を採用しない。外部サービスを使う段階では費用・送信内容・同意設計を先に決め、実セッションは送らない。

## フィードバック反復

各レビュー後に「反応 → 課題 → 優先度 → 変更 → 再レビュー」の記録を残す。発表用デモが完成しても製品の正しさを証明したとはみなさず、利用者の期待と違う場合は前提や画面構成を見直す。
